# 数据安全、备份迁移与多终端访问

## 一、这套 Docker 里到底跑了什么

**一个进程，没有别的服务。** 容器里 PID 1 就是 Node 服务壳，没有独立数据库进程、
没有 nginx、没有 Redis、没有消息队列。镜像 197MB。

| 组件 | 实现 | 位置 |
|---|---|---|
| 数据库 | **SQLite**（WAL 模式，外键约束开启） | `/opt/yonghong/data/platform.sqlite` |
| 文件对象存储 | 本地磁盘，内容寻址（SHA-256 分桶） | `/opt/yonghong/data/r2/` |
| Web 服务 | Node 22 内置 HTTP，静态资源本进程直出 | 容器内 `:8911` |
| 数据库迁移 | 启动时自动比对并应用，已应用的跳过 | `drizzle/*.sql`，12 个 |

数据库共 **42 张表**，分四类：

- **身份权限**：`accounts` / `account_credentials` / `roles` / `permissions` /
  `role_permissions` / `hospital_memberships` / `app_sessions` / `account_mfa_settings`
- **数据管线**：`data_import_jobs` / `raw_datasets` / `data_dataset_snapshots` /
  `data_field_mappings` / `data_cleaning_rules` / `data_quality_issues` /
  `data_publish_versions` / `data_pipeline_records`（Raw→Staging→Curated→Published 四层）
- **业务口径**：`data_metric_definitions` / `data_visualization_definitions` /
  `data_business_templates` / `data_field_definitions` / `benefit_reports` / `report_artifacts`
- **审计留痕**：`audit_logs` / `data_lineage_events` / `data_review_events` /
  `data_reconciliation_runs`

**所有状态都在 `/opt/yonghong/data` 这一个目录里**，没有第二处。备份它 = 备份整个系统。

## 二、数据安全

### 已经做了的

| 项 | 做法 |
|---|---|
| 口令存储 | PBKDF2-SHA256，**21 万次迭代**，每账号独立随机盐；数据库里没有明文也没有可逆密文 |
| 口令比对 | 双方各做一次 SHA-256 后比较，避免逐字符早退的时序侧信道 |
| 暴力破解 | 连续 5 次失败锁定 15 分钟；登录、改密两条路径共用同一套计数 |
| 会话 | `__Host-` 前缀 Cookie，服务端只存 SHA-256 哈希；闲置 8 小时、绝对 24 小时过期 |
| 多因素 | 支持 TOTP 验证器 + 一次性恢复码，密钥用 `MFA_TOTP_ENCRYPTION_KEY` 加密后落库 |
| 权限 | 角色按左侧菜单勾选授权；深链 `?view=` 同样过权限门，绕不过去 |
| 越权防护 | 所有接口按医院隔离；跨院数据在 SQL 层就带 `hospitalId` 条件 |
| 操作留痕 | 登录/改密/权限变更写 `audit_logs`；数据导入/复核/发布写 `data_lineage_events` 与 `data_review_events`，含**破例（break_glass）标记与理由** |
| 职责分离 | 创建人不得复核或发布自己的批次；平台管理员紧急破例必须填 ≥20 字理由并留痕 |
| 传输 | 试用期明文 HTTP；正式部署经 nginx 提供 HTTPS（平台按 `X-Forwarded-Proto` 判定） |

### 还没做的（要如实知道）

- **数据库文件本身没有加密**。`platform.sqlite` 是明文 SQLite，拿到服务器磁盘就能读。
  医院要求落盘加密的话，两条路：给数据盘做腾讯云云硬盘加密（对应用透明，推荐），
  或换 SQLCipher（要改驱动，工作量中等）。
- **备份文件同样是明文**，拷到院外要自己加密：`gpg -c` 或 `openssl enc` 都行。
- **没有自动备份**，需要你挂 cron（下面给了）。

## 三、备份

### 热备份（不停服，推荐）

```bash
docker exec yonghong-platform node -e "
const {DatabaseSync}=require('node:sqlite');
new DatabaseSync('/data/platform.sqlite').exec(\"VACUUM INTO '/data/backup.sqlite'\");
"
mkdir -p /opt/backup
mv /opt/yonghong/data/backup.sqlite /opt/backup/db-$(date +%F-%H%M).sqlite
tar -czf /opt/backup/files-$(date +%F).tar.gz -C /opt/yonghong/data r2
```

`VACUUM INTO` 出来的是**一致性快照**，不会读到写了一半的事务，业务无感知。

### 挂成每天自动备份

```bash
cat > /etc/cron.daily/yonghong-backup <<'EOF'
#!/bin/sh
set -e
D=/opt/backup; mkdir -p $D
docker exec yonghong-platform node -e "
const {DatabaseSync}=require('node:sqlite');
new DatabaseSync('/data/platform.sqlite').exec(\"VACUUM INTO '/data/backup.sqlite'\");
"
mv /opt/yonghong/data/backup.sqlite $D/db-$(date +\%F).sqlite
tar -czf $D/files-$(date +\%F).tar.gz -C /opt/yonghong/data r2
find $D -name 'db-*.sqlite' -mtime +30 -delete
find $D -name 'files-*.tar.gz' -mtime +30 -delete
EOF
chmod +x /etc/cron.daily/yonghong-backup
```

再叠一层腾讯云云硬盘快照（控制台设自动快照策略），就是"本机 + 云端"两份。

### 恢复

```bash
docker stop yonghong-platform
cp /opt/backup/db-2026-08-12.sqlite /opt/yonghong/data/platform.sqlite
rm -f /opt/yonghong/data/platform.sqlite-wal /opt/yonghong/data/platform.sqlite-shm
tar -xzf /opt/backup/files-2026-08-12.tar.gz -C /opt/yonghong/data
docker start yonghong-platform
```

## 四、迁移到另一台服务器

**换机器只需要搬一个目录。** 实测过程如下（已验证数据完全一致）：

```bash
# 旧机器
tar -czf yonghong-data.tar.gz -C /opt/yonghong/data .
scp yonghong-data.tar.gz root@新服务器IP:/root/

# 新机器：装好平台（bash deploy/install-docker.sh），然后
docker stop yonghong-platform
rm -rf /opt/yonghong/data/* 
tar -xzf /root/yonghong-data.tar.gz -C /opt/yonghong/data
docker start yonghong-platform
```

几个关键点：

- **迁移不需要导出导入 SQL**，SQLite 是单文件，跨机器直接拷。
- 新机器启动时会自动比对迁移版本，已应用的 12 个迁移不会重复执行（日志显示"本次新应用 0 个"）。
- **账号密码、角色权限、已发布版本、审计血缘全部跟着走**，用户无感知。
- 升级平台版本和迁移数据是两件独立的事：重装程序不碰 `data` 目录。

### 以后数据量大了怎么办

单院试点 SQLite 完全够用（WAL 模式，读写不互相阻塞）。真到了需要换的时候：

- **SQLite → TencentDB MySQL**：把 drizzle 迁移转 MySQL 方言、换驱动。改动集中在
  `db/` 目录，业务代码不用动。
- **本地磁盘 → 腾讯云 COS**：`server-node/r2-disk.mjs` 是唯一对接点，
  接口只有 put/get/head/delete/list 五个方法，写个 COS 适配器替换即可。

## 五、多终端访问

**不需要装客户端，浏览器打开地址就行。** 已实测四种尺寸：

| 终端 | 分辨率 | 登录 | 数据 | 横向溢出 | 控制台错误 |
|---|---|---|---|---|---|
| PC | 1920×1080 | OK | OK | 0px | 0 |
| 平板 | 1024×768 | OK | OK | 0px | 0 |
| 手机 | 390×844 | OK | OK | 0px | 0 |
| 会议室大屏 | 3840×2160 | OK | OK | 0px | 0 |

- **同一账号可以在多台设备同时登录**，会话各自独立，不互相踢下线（实测 PC/平板/手机
  三端并发登录并访问，全部正常）。每个会话闲置 8 小时、最长 24 小时过期。
- **手机端**侧边菜单收成抽屉，点汉堡按钮展开。
- **大屏**有专门的投屏模式：全屏 + 15 秒轮播 + Esc 退出，适合科室墙上挂着。
- **扫码直达**：单机档案页有二维码，工程师在设备旁边扫一下直接进这台设备的档案页
  （二维码带医院上下文，多院账号扫码会自动切到对应医院）。

### 想让院外也能访问

现在是内网 IP + 端口，出了医院网络就打不开。三个选择：

1. **VPN**（最省事，医院一般已有）——接入院内网后和在办公室一样用；
2. **公网域名 + HTTPS**——需要域名备案，配好后 `--behind-nginx` 模式对外；
3. **腾讯云内网穿透/云联网**——多院区互联时用。

无论哪种，平台侧不用改代码，只是网络接入方式不同。
