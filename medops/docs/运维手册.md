# 运维手册 —— 备份、恢复、证书、升级、故障应急与时间自查

> 读者：系统管理员（设备科）。前提：已按《部署手册.md》完成部署。
> 本文所有命令默认先执行：
>
> ```
> cd /opt/medops/deploy
> ```
>
> （若你的代码放在别处，把 `/opt/medops`、`/opt/data` 换成实际路径；
> git 克隆方式部署时数据目录是 `/opt/app/data`。）

---

## 1. 日常备份

### 1.1 服务器自动备份（无需操作，但要知道）

后端内置定时任务，**每天凌晨 02:30（北京时间）** 自动备份到 `/opt/data/backups/`：

- `app-20260804.db` —— 当天的数据库完整快照（科室/设备/记录/账号等全部业务数据）；
- `files-20260804.tar.gz` —— 当天的签名图与附件打包；
- 自动保留最近 **30 天**，更早的自动删除。

随时可查看备份是否在正常生成（日期应该是最近的）：

```
ls -lh /opt/data/backups/ | tail -5
```

### 1.2 每周下载一份到院内电脑（必须坚持）

自动备份和数据在同一台服务器上——**服务器整机故障时两者一起丢**。
因此固定一个时间（建议每周一上午），把最新备份下载到院内电脑保存：

在**院内电脑**的终端执行（Windows：开始菜单搜 PowerShell；先建好 `D:\医院备份` 文件夹）：

```
scp "root@服务器公网IP:/opt/data/backups/app-$(Get-Date -Format yyyyMMdd).db" D:\医院备份\
```

```
scp "root@服务器公网IP:/opt/data/backups/files-$(Get-Date -Format yyyyMMdd).tar.gz" D:\医院备份\
```

> Mac/Linux 电脑把 `$(Get-Date -Format yyyyMMdd)` 换成 `$(date +%Y%m%d)`，目标路径换成本机目录。
> 当天 02:30 之前下载的话请把日期改成昨天的。
> 不习惯命令行也可以用宝塔面板 / WinSCP 图形界面进入 `/opt/data/backups/` 下载这两个文件。

下载后**打开文件属性确认大小不为 0**，并保留最近 8 周的文件。

## 2. 数据恢复（三步）

适用：误删数据、数据库损坏、换服务器迁移。以恢复 `20260801` 的备份为例。

**第一步：停后端**

```
docker compose stop api
```

**第二步：覆盖数据库 + 解包附件**

```
cd /opt/data && mv app.db app.db.bad-$(date +%s) && rm -f app.db-wal app.db-shm
```

```
cp /opt/data/backups/app-20260801.db /opt/data/app.db
```

```
tar xzf /opt/data/backups/files-20260801.tar.gz -C /opt/data
```

> 说明：第一条把出问题的库改名留底（不直接删）并清掉 WAL 临时文件；
> 第三条把签名图与附件解回 `/opt/data/files/`。
> 若备份文件在院内电脑上，先用 scp 反向传回服务器的 `/opt/data/backups/`。

**第三步：起后端并验证**

```
cd /opt/medops/deploy && docker compose start api
```

```
curl -s https://jx.example.com/api/health
```

输出 `{"ok":true}` 后，用浏览器登录后台抽查：巡检记录还在、签名图能显示。

## 3. 恢复演练（上线第一周必须做一次）

> 没做过恢复演练的备份等于没有备份。趁数据还少、失败无所谓，把流程完整走一遍，
> 之后每半年重复一次。选一个**晚上低峰时段**，全程约 15 分钟。

1. 提前在工作群里说明"今晚 X 点系统维护 10 分钟"；
2. 登录管理后台，记下当前数据量作为对照：科室数、设备数、最近一条巡检记录的日期；
3. 确认今天凌晨的自动备份存在且大小正常：

   ```
   ls -lh /opt/data/backups/ | tail -2
   ```

4. 按上面 **第 2 节的三步** 用今天的备份做一次真实恢复（今天的备份内容≈当前数据，恢复后应无差异）；
5. 验证：管理员能登录、科室/设备数与第 2 步记的一致、随便点开一条已签记录**签名图能显示**（这一步验证的是 files 附件包）、手机端 H5 能登录；
6. 在运维记录本上写下：演练日期、用的备份文件名、耗时、是否成功、遇到的问题。
   **如果哪一步卡住了，现在解决它** ——真出事时没有从容排查的机会；
7. 群里通知维护完成。

## 4. HTTPS 证书排障

证书由 certbot 容器每 12 小时自动检查续期（有效期 90 天、剩 30 天内自动续），正常无需人工干预。

**查看证书状态与到期日：**

```
docker compose run --rm --entrypoint certbot certbot certificates
```

**查看续期日志：**

```
docker compose logs --tail=50 certbot
```

**手动强制续期一次（浏览器提示证书过期时）：**

```
docker compose run --rm --entrypoint certbot certbot renew --webroot -w /var/www/certbot
```

```
docker compose exec web nginx -s reload
```

**续期失败最常见的三个原因：**

| 原因 | 处理 |
|---|---|
| 安全组把 80 端口关了 | 云控制台防火墙重新放行 80 |
| 域名解析被改动/过期 | `ping 域名` 确认仍指向本服务器 IP |
| web 容器没在运行 | `docker compose up -d` 后重试手动续期 |

## 5. 重置管理员密码

超管密码忘了（普通账号请让管理员在后台「账号管理 → 重置密码」处理）：

```
docker compose run --rm api node src/scripts/create-admin.js admin 新密码
```

- `admin` 换成实际管理员账号名，新密码至少 6 位；
- 该命令同时会解除此账号的登录冻结与禁用状态。

## 6. 升级流程

**第一步：更新代码**（git 方式）：

```
cd /opt/app && git pull
```

（scp 方式则重新上传整个 medops 覆盖 `/opt/medops`。数据在 `/opt/data`，不受影响。）

**第二步：按改动范围执行**（前端产物需要 Node 18+ 环境构建，推荐在开发电脑上构建好、
把产物一起提交/上传，服务器上不装 Node）：

| 改了什么 | 需要做什么 |
|---|---|
| `server/`（后端） | `cd /opt/medops/deploy && docker compose build api && docker compose up -d api` |
| `admin/`（管理后台源码） | 开发电脑上 `cd medops/admin && npm run build`，连同生成的 `dist/` 一起发布到服务器，**无需重启**（nginx 直接挂载目录，刷新页面即生效） |
| `ams/`（盘点 shim 或原件升级） | 开发电脑上 `cd medops/ams && node tools/inject-shim.js` 重新生成 `dist/`，发布后即生效 |
| `h5/index.html` | 直接替换文件即生效 |
| `deploy/nginx/`（nginx 配置） | 改完注意别把域名改回占位符；然后 `docker compose exec web nginx -t && docker compose exec web nginx -s reload` |
| `deploy/docker-compose.yml` | `docker compose up -d` |

> **数据库结构升级不用管。** 后端每次启动会自动按顺序执行 `server/src/db/migrations/*.sql`，
> 执行过的记在 `schema_migrations` 表里不会重复执行，**老数据不会被动**。
> 比如 v1.1 的「有效期提醒」给设备表加了 3 列，升级后老设备这几列是空的（=不适用），
> 不会凭空冒出提醒，需要提醒的设备由设备科在后台或用 Excel 补录到期日。
> 想确认迁移是否执行：`docker compose logs api | grep -i migrat`。

**第三步：验证** ——重跑《部署手册》第 8 步验证清单。升级出问题时，git 方式可
`git checkout 上一个版本` 回滚代码后重复上述步骤；数据如受影响按第 2 节恢复当天备份。

## 7. 常见故障速查表

| 现象 | 原因与处理 |
|---|---|
| **https 打不开 / 一直转圈** | 依次排查：① `docker compose ps` 看 web/api 是否 Up，不在则 `docker compose up -d`；② 云控制台防火墙 80/443 是否放行；③ 证书是否过期（见第 4 节）；④ 大陆服务器域名备案是否被注销 |
| **打得开 http 打不开 https** | 证书问题，见第 4 节 |
| **登录提示"账号已冻结"（423）** | 连续输错密码 5 次触发，按提示等几分钟自动解冻；急用时管理员在后台重置该账号密码（重置即解冻），管理员自己被冻结见第 5 节 |
| **登录提示"操作过于频繁"（429）** | 同一网络短时间内登录尝试过多（防撞库保护），等 2 分钟再试；不影响已登录用户 |
| **月报导出失败/超时** | 数据量大时生成需十几秒，耐心等待不要连点；反复失败看后端日志 `docker compose logs --tail=100 api`；一分钟内导出超过 20 次会被限流，稍后再试 |
| **微信里点导出没反应/下载被拦** | 微信内置浏览器不允许下载文件。点右上角"···"→ **在浏览器中打开**，再导出；或改用电脑上的管理后台导出 |
| **手机能打开电脑打不开（或反过来）** | 一般是某一侧网络的 DNS 缓存未更新，换网络试试；医院内网如有上网行为管理，请信息科放行该域名 |
| **签名图不显示（裂图）** | 若发生在恢复数据之后，多半是漏解了 files 附件包，重做第 2 节第二步的 `tar xzf`；个别图裂开则记录时间点找管理员核对审计日志 |
| **磁盘满（网站变慢/写入失败）** | `df -h` 查看；清理旧镜像 `docker image prune -af`；`du -sh /opt/data/*` 看数据占用，备份目录只保留 30 天属正常 |
| **服务器重启后网站没起来** | 容器均配置了自动重启，等 2 分钟；还不行 `cd /opt/medops/deploy && docker compose up -d` |
| **签字日期不对（签的是昨天/明天）** | 服务器时间不准，见第 9 节自查 |

## 8. 服务器故障应急预案

> **这一节要在上线前讲给所有护士长和巡检员听。**
> 一句话版本：**打不开就先记在纸上，恢复后进系统补录补签，一切照常。**

### 为什么不用慌

系统允许**补签过去的日期**（只是不允许提前签未来的日期）。所以服务器停一天、两天，
恢复后把这几天补录上去，周签、月签照常结算，不会因为断了一天就卡死。

### 一线人员的做法（护士长/巡检员）

| 情况 | 怎么办 |
|---|---|
| 手机打不开巡检页面 | 先在纸上记录：日期、设备、正常/异常、异常描述、巡检人 |
| 系统恢复后 | 进系统选择**当时的日期**，照纸上内容补录、补签 |
| 当周日签补齐后 | 护士长照常周签 |
| 当月周签补齐后 | 设备科照常月签 |

> 纸质记录先别扔，等补录完并核对无误后再归档。

### 管理员的做法

1. **先判断范围**——是所有人都打不开，还是只有某个人的手机？
   - 只有一个人 → 多半是他的网络或账号问题，看第 7 节速查表
   - 所有人都打不开 → 继续下面步骤

2. **看服务器还在不在**（SSH 登录服务器）：

```
cd /opt/medops/deploy && docker compose ps
```

- 容器不是 `Up` → `docker compose up -d`，等 2 分钟再试
- SSH 都连不上 → 云控制台看服务器是否关机/欠费，或联系机房（内网部署）

3. **恢复不了、预计要停很久**，通知临床按上面"一线人员的做法"走纸质，
   同时按第 2 节从备份恢复数据。

4. **恢复之后**：登录管理后台首页看"未签提醒"，按名单点对点通知补签。

### 什么情况会真丢数据

只有一种：**服务器整机损坏，且从未把备份下载到别处**。
这就是第 1 节要求每周下载备份到院内电脑的原因——那是唯一的最后防线。

## 9. 服务器时间与时区自查

### 为什么重要

整套三级签字的"今天是哪天""这周属于哪周""这个月归哪个月"，**全部由服务器裁决**
（客户端改手机时间无效，这是防止提前签字的设计）。所以**服务器时间不准 = 签字日期全错**，
而且这种错很隐蔽，往往过很久才被发现。

### 三条自查命令

在服务器上依次执行：

```
date
```

看日期和时间对不对（下一条会解释时区问题）。

```
timedatectl
```

看 `System clock synchronized: yes` 表示时间正在自动同步（公网服务器通常自带，无需处理）。
若显示 `no`，见下方"时间没有自动同步怎么办"。

```
cd /opt/medops/deploy && docker compose exec api date
```

看容器内的时间，应与宿主机一致。

### 关于时区：不必纠结，但要知道原理

- 容器已设置 `TZ=Asia/Shanghai`（见 `docker-compose.yml`），**但这只影响日志的时间戳**；
- **业务日期不依赖容器时区**——代码里用 `Asia/Shanghai` 显式换算
  （`server/src/services/period.service.js`），即使容器时区是 UTC，业务日期依然正确；
- 真正要保证的只有一件事：**服务器的绝对时间要准**（几秒误差无所谓，几小时就有问题）。

### 最直观的验证方法（推荐用这个）

不用记命令，登录**管理后台首页**，看右上角的"服务器时间"：

- 显示的应当是**当前北京时间**（含日期和时分）；
- 与你手机上的时间对得上 → 一切正常；
- 差了几小时或日期不对 → 按下面处理。

### 时间没有自动同步怎么办

公网服务器一般自带时间同步。内网服务器可能连不上公网 NTP，需要处理：

```
sudo timedatectl set-ntp true
```

若内网无法访问公网 NTP，请信息科提供**院内 NTP 服务器地址**，
写入 `/etc/systemd/timesyncd.conf` 的 `NTP=` 一行后重启服务：

```
sudo systemctl restart systemd-timesyncd && timedatectl
```

实在没有 NTP 可用时，可手动设置一次（治标不治本，需定期复查）：

```
sudo timedatectl set-time "2026-09-01 08:30:00"
```

> 手动设置的服务器建议**每月自查一次**，硬件时钟长期运行会漂移。
